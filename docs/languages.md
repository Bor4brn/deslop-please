# Languages

`deslop-please` reads every language the same way: an indexer writes a
[SCIP](https://github.com/sourcegraph/scip) index of the project, the index and
the files' text become one plain model (modules, files, items, the references
between them, and the functions that only wrap others), and the lints read the
model. The lints, the graph and the report know nothing of the language.

```
                  detect (src/languages/detect.rs)
                         │ projects: language, root, source files
        ┌────────────────┼──────────────────────────┐
        ▼                ▼                          ▼
  rust-analyzer      scip-python             scip-typescript
  (src/indexing.rs)  (src/languages/index.rs, cached outside the project)
        │                │                          │
        ▼                └────────────┬─────────────┘
  model/from_index                    ▼
  (Rust's syntax)            model/from_scip (Python, TypeScript/JavaScript)
        └────────────────┬────────────┘
                         ▼
                  model::Model ──▶ graph ──▶ lint ──▶ format
```

Each project gets a model of its own and its own run of the lints; the
reports are put together, sorted, and their paths start from where the run
started.

## The indexers

| | scip-python | scip-typescript |
| --- | --- | --- |
| What it is | Sourcegraph's fork of Pyright, the type checker | Sourcegraph's indexer on the TypeScript compiler |
| Tested with | 0.6.8 | 0.5.2 (0.6 needs Node.js 22.23.4 or later) |
| Command | `scip-python index --project-name <name> --project-version 0 --cwd <root> --output <cache>` | `scip-typescript index --cwd <root> --output <cache> <tsconfig.json>` |

Both are maintained and released through 2026, write the same SCIP format
rust-analyzer does, and resolve names with the language's own type checker, so
`queue.items` in another module resolves to the class's `items` wherever the
checker can tell what `queue` is. CI pins both versions, as it pins
rust-analyzer's: the index is part of what the lints report.

Two choices keep the projects untouched:

- scip-typescript's `--infer-tsconfig` writes a `tsconfig.json` into a project
  that has none. Instead, `deslop-please` writes one to its cache directory
  that lists the project's files by absolute path (`allowJs`, no emit), and
  passes that.
- Indexes are cached under `$XDG_CACHE_HOME/deslop-please/` (else
  `~/.cache/deslop-please/`), one directory per project, with a stamp of the
  indexer's version, the manifests and every source file's hash. Rust's index
  stays in the workspace's `target/`, as before.

The indexers are not downloaded at run time (no `npx`): a missing indexer is
an error that says how to install it.

## Finding projects

One walk of the tree from the current directory:

| Family | A project is a directory with |
| --- | --- |
| Rust | `Cargo.toml` in the current directory or above it (`cargo metadata` finds the workspace, as before), else each outermost `Cargo.toml` below it |
| Python | `pyproject.toml`, `setup.py`, `setup.cfg`, `requirements.txt` or `Pipfile` |
| TypeScript, JavaScript | `package.json`, or `tsconfig.json` outside a `package.json` project |

A project holds the source files below it, less those of a project of the
same family nested in it, so each package of a monorepo is a project of its
own. It is TypeScript if it has a `.ts`/`.tsx`/`.mts`/`.cts` file, else
JavaScript. A project whose only sources are tools' configuration
(`*.config.js`, `setup.py`, `conftest.py`) is left out, so a Django project
with a `tailwind.config.js` needs no TypeScript indexer.

Never read: hidden directories (`.git`, `.venv`, `.next`, ...), `node_modules`,
`bower_components`, `jspm_packages`, `site-packages`, `__pycache__`,
`__generated__`, `target`, `dist`, `build`, `out`, `coverage`, `htmlcov`, test
data (`fixtures`, `__fixtures__`, `testdata`, `__snapshots__`), any directory
holding a `pyvenv.cfg` (a virtual environment, whatever its name), declaration
files (`*.d.ts`), and generated files: `*.min.*`, `*.generated.*`, `*_pb2.py`,
`*_pb.*`, `*.pb.*`, and files whose first lines say `@generated`,
`DO NOT EDIT`, `auto-generated` or `Code generated by`.

`--language <name>` keeps the projects of one language. Asked for by name, a
language needs no manifest: with none found, the current directory is the
project, so `deslop-please --language python` checks a folder of scripts.

## What the model reads

| | Python | TypeScript / JavaScript |
| --- | --- | --- |
| Package | the project, named by `pyproject.toml`'s `name` or its directory | the project, named by `package.json`'s `name` or its directory |
| Module | a package or module: `app/store/table.py` is `app::store::table`; `__init__.py` is its directory | a directory or file: `src/store/table.ts` is `store::table`; `index.ts` is its directory |
| Root | a top-level package of the project's own name (`boot/` in the project `boot`) is the package's root, as `lib.rs` is a crate's; a leading `src/` is no level | a leading `src/` is no level |
| Types | classes (nested ones are part of theirs) | classes, interfaces, enums, type aliases |
| Functions | functions and methods; `__dunder__` methods count as a trait's do in Rust (Python calls them, code does not) | functions, methods, constructors, getters and setters, `const f = () => ..`, and properties that hold a function (`get = <T>(path: string) => ..`, `onChange: (v: string) => void`), which code calls as methods |
| Fields | class attributes, dataclass fields and `self.x` attributes | class properties, parameter properties (`constructor(private x: T)`), class-body fields of JavaScript classes, and the members of an object type alias (`type Row = { id: number }` has the field `Row::id`); a member of an object type written in a signature or a type argument names nothing |
| References | every name outside `import`/`from` statements | every name outside `import`, `export ... from`, `export { .. }` and `const x = require(..)` |
| Tests | `test_*.py`, `*_test.py`, `conftest.py`, `tests/`, `test/` | `*.test.*`, `*.spec.*`, `*.stories.*`, `__tests__/`, `__mocks__/`, `tests/`, `test/`, `e2e/`, `cypress/` |

As in Rust, a re-export (`__init__.py`, `index.ts`) is no use, so a barrel file
neither makes nor hides a cycle.

## Each lint, per language

### `module-cycle`

Sibling modules whose code names each other's items, in a circle. In Python an
import behind `if TYPE_CHECKING:` or written for an annotation ties the
modules as any other: the code still needs the other module to be read.
Packages are kept in order by their package managers, as crates are by Cargo,
so no cycle is between two projects.

### `tangle`

Types, functions and constants that know each other in a circle, across
modules or more than seven of them. Same in every language.

### `field-leak`

A class guards its fields when it keeps at least one to itself and has a
method of its own that works on them; then a field that code outside it
writes, indexes, deletes, reaches into or passes on is known outside. Reading
a scalar is no leak: what a field holds is judged from its annotation
(`int`, `str`, `bool`, `float`, `bytes`, `Optional[..]` in Python; `number`,
`string`, `boolean`, `bigint`, literal types in TypeScript; an array such as
`number[]` is no scalar) or, without one, from its first value (`= 0`,
`= "x"`, `= True`, or a parameter annotated so). Reaching into a field for a
member that is only read is a read of it, as in Rust: `user.address.city`,
`queue.limit().most`.

Accessors are seen through by Rust's rule: a method whose body names fields of
its own class and nothing else of the project's, and computes nothing (no
literal, no operator but `=`, no branching keyword, no index, no new value, no
call but of a parameter), however it is laid out. `return self._items`, a
`@property`, `get items()`, `items = self._items; return items`, a tuple
`return (self._items, self._head)`, `return each(this.items)` lending a field to
a callback, and a setter all are; what the signature names plays no part. What
it overwrites, or what is no scalar, it lends; a scalar it only hands out it
copies. A method that only passes the call on to a field is a forwarder, as in
Rust.
A constructor (`__init__`, `constructor`) works on no instance, as Rust's
`new`; a class whose only method is one is a record, and guards nothing.

Limits:

- A number handed out in a tuple, `items, head = queue.parts()`, is a copy:
  Python and JavaScript have no `&mut usize` to write it back through, so it
  is not known outside, where Rust's `parts_mut` makes it so.
- A value object kept in a local and read later, `limit = queue.limit();
  limit.most`, is not followed through the local; read on the spot,
  `queue.limit().most`, it is.
- **JavaScript:** scip-typescript gives a field that only `this.items = []` in
  a constructor declares a symbol local to its file, not a property of the
  class, so its leaks are not seen. Fields declared in the class body
  (`items = [];`), `#private` fields, and TypeScript are not affected.
- In Python and plain JavaScript a reference is only seen where the type
  checker knows what the object is; annotate the parameter (or use JSDoc in
  JavaScript) for the leaks through it to be seen.
- TypeScript names both a property's getter and setter where code names the
  property; the setter is taken where the code assigns to it, the getter
  elsewhere.

### `shallow-module`

A package, or a module with child modules, that shows more functions than a
reader holds in mind, at least as many as it hides, and a list that long.
Python's constructor is the class (`Store()` names the class, not
`__init__`), so it is not counted; TypeScript's `new Store()` names the
constructor, which counts as a function shown, as Rust's `Store::new` does.

### `wide-directory`, `long-file`

A directory of more than fifteen source files and directories, a file of more
than 2,000 lines: the sources are the project's indexed files, of its own
language.

## Same code, same reports

Every restructuring of the Rust fixtures (`tests/fixtures`, `tests/variants`)
that has a meaning in Python and TypeScript is written in both, and
`tests/languages.rs` checks that each reports the same keys as Rust's, by the
language's names:

| Lint | Restructurings, each in Python and TypeScript |
| --- | --- |
| `module-cycle` | the cycle; through a re-export; through a relay (three modules); the constant moved to its user; a cycle only test code makes |
| `tangle` | across two modules; the type lifted into the parent module; both merged into one module; untied by a function above them; eight types in a ring in one module |
| `field-leak` | fields reached directly; through getters and setters; through getters with locals and a callback; through a tuple getter (see above); free functions pasted beside the class; the work moved into the class; passed on to an inner object; only scalars read; a value object read through a getter |
| `shallow-module` | the wide store; padded with private helpers, getters and forwarders; its methods made free functions; methods that only forward; made deep; small types that each show a few |
| `wide-directory`, `long-file` | 2,000 lines and 15 files pass, one more of each does not |

What only Rust has (`cfg`, features and targets, build scripts, `include!`,
`impl` blocks written elsewhere, crates of one workspace) has no counterpart.
Rust's own reports are unchanged: on every Rust fixture and variant, with each
of the flags the tests use, in text, JSON and SARIF, the output is byte for
byte that of `deslop-please` 0.1.6.

## Known limitations

- Each package of a JavaScript or Python monorepo is a project of its own, so
  a field one package leaks to another is not seen (Rust's crates of one
  workspace are one model, as before).
- Dynamic code is not seen: `getattr`, `eval`, string-keyed property access,
  monkey patching, and calls the type checker cannot resolve.
- A TypeScript project is indexed by its own `tsconfig.json`; files it does
  not include are not read. If it includes none of them, that is an error.
- A JavaScript or TypeScript file that a regular expression or a JSX text with
  an apostrophe confuses is still indexed rightly; only the token reading that
  decides reads and writes near it may judge a field's access wrongly, on that
  line.

## Adding a language

The lints need no change. A language needs:

1. **A variant of `Language`** in `src/languages/mod.rs`, with its name for
   `--language`.
2. **Its projects:** the manifests that make one, and its source files'
   extensions, in `src/languages/detect.rs` (`family`, and `walk` for the
   manifests).
3. **Its indexer:** a SCIP indexer, run in `src/languages/index.rs` with the
   command that writes the index to the cache, and the install hint in
   `missing`.
4. **How its symbols name modules:** if the indexer writes symbols as
   scip-python's (a dotted module name) or scip-typescript's (a file path)
   do, give the language one of `model::Syntax`'s variants; otherwise add a
   variant with its `module_path`, its test files and modules, and in
   `model/from_scip/text.rs` its comments, strings and import statements.
5. **Fixtures:** a base project and its variants under `tests/fixtures/` and
   `tests/variants/`, with a test in `tests/languages.rs` for each lint, and a
   clean project that reports nothing.

A language whose indexer is not SCIP needs its own builder of the model, as
Rust's `model/from_index` is: what the lints read is only `model::Model`.
